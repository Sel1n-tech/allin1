# 📘 Полное руководство по Git: От настройки до чистого Pull Request

Это исчерпывающая шпаргалка и пошаговый сценарий работы в Git: от первоначальной настройки компьютера и создания репозитория до фиксации изменений, синхронизации с командой, решения конфликтов и «сжатия» (squash) истории коммитов.

---

## ⚙️ Часть 0: Первоначальная настройка Git

### 📝 Краткая сводка
Первое, что нужно сделать после установки Git — настроить свою личность и окружение. Каждый коммит содержит имя и email, и изменить их задним числом сложно.

Git хранит настройки на трёх уровнях:
1. **`--system`**: Для всех пользователей компьютера (требует прав администратора). Файл: `[path]/etc/gitconfig` (Linux) или `C:\ProgramData\Git\config` (Windows).
2. **`--global`**: Для текущего пользователя во всех его репозиториях. Файл: `~/.gitconfig` или `~/.config/git/config`.
3. **`--local`**: Только для текущего репозитория. Файл: `.git/config`. Это уровень по умолчанию.

### 🛠️ Шпаргалка по настройке

| Команда | Что делает |
| :--- | :--- |
| `git config --global user.name "Имя"` | Устанавливает ваше имя для всех коммитов. |
| `git config --global user.email "email@dom.ru"` | Устанавливает ваш email для всех коммитов. |
| `git config --global core.editor nano` | Задаёт текстовый редактор по умолчанию (`nano`, `vim`, `code --wait`). |
| `git config --global init.defaultBranch main` | Делает ветку `main` стандартной при создании новых репозиториев. |
| `git config --global alias.st status` | Создаёт псевдоним (сокращение). Теперь `git st` работает как `git status`. |
| `git config --list --show-origin` | Показывает все текущие настройки и файлы, из которых они были загружены. |

### 💡 Типичные сценарии настройки

**Первая настройка компьютера:**
```bash
git config --global user.name "Ivan Ivanov"
git config --global user.email "ivan@example.com"
git config --global init.defaultBranch main
git config --global core.editor "code --wait"  # VS Code
```

### Настройка удобных сокращений (aliases):
```bash
git config --global alias.co checkout
git config --global alias.br branch
git config --global alias.ci commit
git config --global alias.st status

## 📂 Часть 1: Создание и клонирование репозитория

### 📝 Краткая сводка

Для начала работы репозиторий нужно либо создать из существующей папки (`git init`), либо клонировать с сервера (`git clone`).

### 🛠️ Шпаргалка по инициализации

| Команда | Что делает |
| --- | --- |
| `git init` | Создаёт новый пустой Git-репозиторий (папку `.git`) в текущем каталоге. |
| `git clone <url> [имя_папки]` | Скачивает существующий репозиторий по URL и создаёт его локальную копию. |

### 💡 Типичные сценарии

#### Начало работы над новым проектом с нуля

```bash
cd /path/to/my_project      # Linux/macOS
cd C:/Users/user/my_project # Windows

git init                    # Превращает папку в Git-репозиторий
```

#### Получение существующего проекта

```bash
git clone https://github.com/user/repo.git
# Создаст папку repo

git clone https://github.com/user/repo.git my_custom_name
# Создаст папку my_custom_name
```

## 📋 Часть 2: Локальная работа и жизненный цикл файлов

### 📝 Краткая сводка

- **Состояния файлов:** файлы бывают отслеживаемыми (Git знает о них) и неотслеживаемыми (новые файлы). Отслеживаемые файлы могут быть неизменёнными, изменёнными или подготовленными к коммиту (проиндексированными).
- **Индекс (Staging Area):** промежуточная область подготовки. Чтобы изменение попало в коммит, его нужно сначала добавить в индекс.
- **Игнорирование:** файл `.gitignore` позволяет исключить из отслеживания временные файлы: логи, `node_modules`, сборки и т. д.
- **Просмотр изменений:** `git status` показывает, какие файлы изменены, а `git diff` показывает, что именно изменилось в коде построчно.

### 🛠️ Шпаргалка по локальным командам

| Команда | Что делает |
| --- | --- |
| `git status` или `git st` | Показывает состояние файлов: изменённые, проиндексированные, неотслеживаемые. |
| `git status -s` | Краткий вывод статуса: `M` — изменён, `A` — добавлен, `??` — неотслеживаемый. |
| `git add <файл>` | Добавляет новый файл под контроль версий или индексирует изменения в существующем файле. |
| `git diff` | Показывает изменения в файлах, которые ещё не добавлены в индекс. |
| `git diff --staged` | Показывает изменения, которые уже добавлены в индекс и войдут в следующий коммит. |
| `git commit -m "сообщение"` или `git ci` | Создаёт снимок состояния, то есть коммит, всех проиндексированных файлов. |
| `git commit -a -m "сообщение"` | Автоматически индексирует и коммитит изменения во всех уже отслеживаемых файлах. Пропускает `git add`. Новые файлы не добавляет. |
| `git rm <файл>` | Удаляет файл из индекса Git и из рабочего каталога на диске. |
| `git rm --cached <файл>` | Удаляет файл только из индекса Git, но оставляет его на диске. Полезно для исправления ошибок в `.gitignore`. |
| `git mv <старое> <новое>` | Переименовывает или перемещает файл и сразу подготавливает это изменение к коммиту. |

### 💡 Типичные локальные сценарии

- **Добавление нового файла:**

  ```bash
  git add README.md
  git commit -m "Добавлен README"
  ```

- **Исправление бага:**

  ```bash
  git diff
  git add app.js
  git commit -m "Исправлена ошибка"
  ```

- **Очистка от мусора:**

  ```bash
  # Добавить *.log в .gitignore
  git rm --cached -r logs/
  git commit -m "Удалены логи из отслеживания"
  ```

### 📌 Правила для `.gitignore`

- Пустые строки и строки, начинающиеся с `#`, игнорируются.
- Стандартные шаблоны применяются рекурсивно для всего дерева каталогов.
- Слеш `/` в начале шаблона отменяет рекурсию.
- Слеш в конце шаблона означает каталог, например `build/`.
- Восклицательный знак `!` инвертирует шаблон.
- Две звёздочки `**` указывают на вложенные каталоги, например `a/**/z`.

#### Пример `.gitignore`

```gitignore
# Исключить все файлы с расширением .a
*.a

# Но отслеживать файл lib.a, даже если он подпадает под исключение выше
!lib.a

# Игнорировать всё содержимое каталога build/
build/

# Игнорировать все .txt файлы в каталоге doc/ и его подкаталогах
doc/**/*.txt
```

## 🌐 Часть 3: Работа с удалёнными репозиториями

### 📝 Краткая сводка

- Удалённые репозитории — это версии проекта, хранящиеся где-то ещё: на GitHub, GitLab, локальном сервере или даже в другом каталоге на том же компьютере.
- `origin` — имя удалённого репозитория по умолчанию при клонировании.
- **Получение данных:**
  - `git fetch` только скачивает изменения, не трогая ваши файлы.
  - `git pull` скачивает изменения и сразу пытается слить их с вашей текущей веткой.
- **Отправка данных:**
  - `git push` загружает ваши локальные коммиты на сервер.
  - Если на сервере есть новые изменения, `push` будет отклонён до синхронизации.
- **Управление ссылками:**
  - Вы можете добавлять, переименовывать и удалять ссылки на удалённые репозитории.

### 🛠️ Шпаргалка по удалённым командам

| Команда | Что делает |
| --- | --- |
| `git remote` | Выводит список имён настроенных удалённых репозиториев. |
| `git remote -v` | Выводит список репозиториев с URL-адресами для чтения (`fetch`) и записи (`push`). |
| `git remote add <имя> <url>` | Добавляет новый удалённый репозиторий и присваивает ему короткое имя. |
| `git fetch <имя>` | Загружает новые данные и ветки из репозитория, не изменяя вашу текущую рабочую копию. |
| `git pull` | Загружает изменения из удалённой ветки и автоматически сливает их с вашей текущей локальной веткой. |
| `git push <имя> <ветка>` | Отправляет ваши локальные коммиты указанной ветки в удалённый репозиторий. |
| `git remote show <имя>` | Показывает подробную информацию об удалённом репозитории: URL, отслеживаемые ветки, настройки pull/push. |
| `git remote rename <старое> <новое>` | Переименовывает удалённый репозиторий. Автоматически обновляет имена веток, например `pb/master` → `paul/master`. |
| `git remote remove <имя>` | Удаляет ссылку на удалённый репозиторий и все связанные настройки отслеживания. |

### 💡 Типичные сценарии синхронизации

- **Синхронизация перед работой:**

  ```bash
  git pull
  ```

  Или более безопасно:

  ```bash
  git fetch origin
  git merge origin/main
  ```

- **Публикация своих изменений:**

  ```bash
  git push origin main
  ```

  Если push отклонён:

  ```bash
  git pull
  # разрешить конфликты
  git push origin main
  ```

- **Добавление репозитория коллеги:**

  ```bash
  git remote add colleague https://...
  git fetch colleague
  ```

  Затем можно работать с веткой, например:

  ```bash
  colleague/branch
  ```

## 🚀 Часть 4: Полный сценарий работы — от ветки до чистого Pull Request

### 🌿 Шаг 1: Создание ветки для задачи

**Правило:** никогда не работайте напрямую в ветке `main`. Всегда создавайте отдельную ветку для задачи.

```bash
# 1. Убеждаемся, что мы в актуальной ветке main и она синхронизирована с сервером
git pull origin main

# 2. Создаём новую ветку для нашей фичи и сразу переключаемся на неё
# 'switch -c' — это современная и понятная альтернатива устаревшему 'checkout -b'
git switch -c feature/add-login-button
```

💡 **Что произошло:** вы создали изолированное пространство. Все ваши изменения здесь не повлияют на `main`, пока вы явно этого не захотите.

---

### 📝 Шаг 2: Внесение изменений и первые коммиты

```bash
# 1. Проверяем, что видит Git. Изменённые файлы будут выделены красным.
git status

# 2. Добавляем конкретный файл в индекс, то есть готовим к коммиту.
git add src/login.js

# 3. Делаем первый черновой коммит.
git commit -m "WIP: добавлена базовая разметка кнопки"

# ... вы продолжаете работать, находите опечатку, исправляете ...

# 4. Снова добавляем и коммитим. История начинает засоряться мелкими правками.
git add src/login.js
git commit -m "fix: исправлена опечатка в тексте кнопки"

git add README.md
git commit -m "docs: обновил readme"
```

⚠️ **Ситуация:** теперь у вас в ветке три маленьких «грязных» коммита. В идеале их нужно объединить в один перед отправкой. Но сначала смоделируем конфликт.

---

### ⚔️ Шаг 3: Обновление ветки и решение конфликта

Пока вы работали, коллега уже отправил свои изменения в `main`, и он тоже менял файл `src/login.js`. Вам нужно подтянуть его изменения.

```bash
# 1. Получаем свежие данные с сервера, не меняя свои файлы.
git fetch origin

# 2. Перебазировываем нашу ветку поверх актуального main.
# Это лучший способ обновить feature-ветку, сохраняя линейную историю.
git rebase origin/main
```

🛑 **СТОП!** Git остановился и выдал ошибку:

```text
CONFLICT (content): Merge conflict in src/login.js
```

Git не знает, какую версию строки оставить: вашу или коллеги.

#### 🛠️ Как решить конфликт

Откройте файл `src/login.js` в вашем редакторе. Вы увидите специальные маркеры:

```text
<<<<<<< HEAD
// Ваш код (Current Change)
=======
// Код коллеги (Incoming Change)
>>>>>>> commit-hash-коллеги
```

- **В VS Code:** над блоком появятся ссылки:
  - `Accept Current Change`
  - `Accept Incoming Change`
  - `Accept Both Changes`

  Выберите нужное.

- **В Vim/Nano:** вручную удалите строки:

  ```text
  <<<<<<<
  =======
  >>>>>>>
  ```

  и оставьте только тот код, который должен остаться в итоге.

Сохраните файл.

#### 🛠️ Завершение разрешения конфликта в терминале

```bash
# 1. Говорим Git, что мы исправили файл, и добавляем его в индекс.
git add src/login.js

# 2. Продолжаем процесс перебазирования.
git rebase --continue
```

💡 **Готово!** Ваша ветка теперь включает в себя последние изменения из `main`, и конфликтов больше нет.

### 🗜️ Шаг 4: «Сжатие» (squash) коммитов

Теперь, когда ветка актуальна, мы хотим превратить наши три черновых коммита в один красивый и понятный.

```bash
# Запускаем интерактивный rebase.
# HEAD~3 означает "взять последние 3 коммита".
git rebase -i HEAD~3
```

Откроется редактор, например VS Code, Nano или Vim, со списком ваших коммитов. Сверху старые коммиты, снизу новые:

```text
pick a1b2c3d WIP: добавлена базовая разметка кнопки
pick e4f5g6h fix: исправлена опечатка в тексте кнопки
pick i7j8k9l docs: обновил readme
```

#### Ваши действия в редакторе

1. Оставьте первый коммит как `pick`. Это будет основа.
2. Замените слово `pick` на `squash` или просто `s` у второго и третьего коммита.

   Это скажет Git: «возьми эти изменения, но приклей их к предыдущему коммиту».

```text
pick a1b2c3d WIP: добавлена базовая разметка кнопки
squash e4f5g6h fix: исправлена опечатка в тексте кнопки
squash i7j8k9l docs: обновил readme
```

3. Сохраните файл и закройте его. См. шпаргалку по редакторам ниже.

#### Второй шаг

Редактор откроется снова, предлагая написать итоговое сообщение коммита. Git объединил тексты всех трёх коммитов.

Удалите старый мусор — строки, начинающиеся с `#`.

Напишите одно чистое сообщение:

```text
feat: добавлена кнопка входа и обновлена документация

- Реализована базовая разметка и логика кнопки
- Исправлены опечатки в интерфейсе
- Добавлено описание в README
```

Сохраните и закройте файл.

💡 **Результат:** вместо трёх коммитов теперь остался один идеальный коммит, который стоит поверх актуального `main`.

### 🚀 Шаг 5: Отправка на сервер (push)

```bash
# Отправляем нашу чистую ветку на удалённый сервер.
# Флаг -u связывает локальную ветку с удалённой для будущих простых push.
git push -u origin feature/add-login-button
```

⚠️ **ВАЖНО:** если вы уже успели сделать `git push` своих трёх «грязных» коммитов на сервер до того, как сделали squash, обычный `git push` будет отвергнут, потому что история изменилась.

В этом случае используйте безопасную принудительную отправку:

```bash
git push --force-with-lease origin feature/add-login-button
```

Никогда не используйте просто `git push -f`. Флаг `--force-with-lease` безопаснее, так как он проверит, не записал ли кто-то другой новый код в эту ветку, пока вы делали squash.

## ⚠️ Важные примечания и лучшие практики

### Безопасность: `fetch` vs `pull`

- `git fetch` абсолютно безопасен: он только скачивает данные в фоновый кэш Git.
- `git pull` сразу меняет ваши файлы. Используйте его, когда уверены, что хотите слить изменения прямо сейчас.

### Настройка `pull.rebase`

Git может предупреждать о неустановленной настройке. Чтобы сделать историю коммитов линейной и чистой, рекомендуется включить rebase по умолчанию:

```bash
git config --global pull.rebase true
```

Если предпочитаете классические коммиты слияния, используйте:

```bash
git config --global pull.rebase false
```

### Правила `.gitignore`

Настраивайте `.gitignore` до начала серьёзной работы. Если файл уже попал в индекс, его нужно сначала удалить через:

```bash
git rm --cached <файл>
```

а затем добавить в `.gitignore`.

### Коммит с подробностями

Используйте флаг `-v` при коммите:

```bash
git commit -v
```

Это позволит увидеть дифф, то есть различия изменений, прямо в редакторе сообщения коммита. Это помогает писать более точные и осмысленные описания.

## 🛠️ Приложение A: Шпаргалка по редакторам Vim и Nano

Если вы не настроили VS Code как редактор по умолчанию, Git откроет Nano на многих Linux-системах или Vim на macOS и некоторых Linux-системах.

Новички часто «застревают» в этих редакторах. Вот как действовать.

### 🟢 Nano — простой и дружелюбный

Внизу экрана всегда есть подсказки с горячими клавишами. Символ `^` означает клавишу `Ctrl`.

| Действие | Комбинация клавиш |
| --- | --- |
| Начать редактировать | Просто печатайте. Вы уже в режиме ввода. |
| Сохранить изменения | `Ctrl + O`, буква `O`, не ноль. Затем нажмите `Enter` для подтверждения имени файла. |
| Выйти из редактора | `Ctrl + X`. Если есть несохранённые изменения, редактор спросит `Save modified buffer?`. Нажмите `Y`, затем `Enter`. |
| Поиск текста | `Ctrl + W`, введите слово, нажмите `Enter`. |

### 🔴 Vim — мощный, но требует понимания режимов

Vim имеет два основных режима:

- **Normal** — для команд.
- **Insert** — для ввода текста.

По умолчанию вы всегда попадаете в режим Normal.

| Действие | Комбинация клавиш |
| --- | --- |
| Перейти в режим ввода | Нажмите `i`, то есть Insert. Теперь вы можете печатать текст как в обычном блокноте. |
| Вернуться в режим команд | Нажмите `Esc`. Делайте это всегда перед сохранением или выходом. |
| Сохранить и выйти | В режиме Normal наберите `:wq` и нажмите `Enter`. Означает Write and Quit. |
| Выйти без сохранения | В режиме Normal наберите `:q!` и нажмите `Enter`. Означает Quit force. Полезно, если вы случайно открыли не тот файл. |
| Отменить последнее действие | В режиме Normal нажмите `u`. Означает Undo. |
| Перемещение по тексту | Стрелки на клавиатуре или в режиме Normal: `h` — влево, `j` — вниз, `k` — вверх, `l` — вправо. |

💡 **Лайфхак для Vim при squash/rebase:** если вы открыли список коммитов для rebase, нажмите `i`, измените `pick` на `s`, нажмите `Esc`, затем наберите `:wq` и нажмите `Enter`.

## 🔄 Приложение B: Шпаргалка по отмене действий

| Действие | Команда |
| --- | --- |
| Отменить `git add` до коммита | `git restore --staged <файл>` |
| Отменить последний коммит, но оставить изменения в файлах | `git reset --soft HEAD~1` |
| Полностью отменить последний коммит и удалить изменения в файлах. ОПАСНО | `git reset --hard HEAD~1` |
| Прервать застрявший rebase | `git rebase --abort` |
| Прервать застрявший merge | `git merge --abort` |

💡 **Совет:** сохраните этот файл в корне вашего проекта или в личном хранилище знаний как `GIT-GUIDE.md` для мгновенного доступа во время работы.
