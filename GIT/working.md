# Полное руководство по основам Git: От настройки до удалённых репозиториев

Это структурированная шпаргалка по работе с Git: от первоначальной настройки и создания репозитория до фиксации изменений и синхронизации с командой.

---

## ⚙️ Часть 0: Первоначальная настройка и создание репозитория

### 📝 Краткая сводка
Первое, что нужно сделать после установки Git — настроить свою личность и окружение. Каждый коммит содержит имя и email, и изменить их задним числом сложно. 
Git хранит настройки на трёх уровнях:
1. **`--system`**: Для всех пользователей компьютера (требует прав администратора).
2. **`--global`**: Для текущего пользователя во всех его репозиториях (файл `~/.gitconfig`).
3. **`--local`**: Только для текущего репозитория (файл `.git/config`). Это уровень по умолчанию.

Для начала работы репозиторий нужно либо **создать** из существующей папки (`git init`), либо **клонировать** с сервера (`git clone`).

### 🛠️ Шпаргалка по настройке и инициализации

| Команда | Что делает |
| :--- | :--- |
| `git config --global user.name "Имя"` | Устанавливает ваше имя для всех коммитов. |
| `git config --global user.email "email@dom.ru"` | Устанавливает ваш email для всех коммитов. |
| `git config --global core.editor nano` | Задаёт текстовый редактор по умолчанию (например, `nano`, `vim` или `code --wait`). |
| `git config --global alias.st status` | Создаёт псевдоним (сокращение). Теперь `git st` работает как `git status`. |
| `git config --list --show-origin` | Показывает все текущие настройки и файлы, из которых они были загружены. |
| `git init` | Создаёт новый пустой Git-репозиторий (папку `.git`) в текущем каталоге. |
| `git clone <url> [имя_папки]` | Скачивает существующий репозиторий по URL и создаёт его локальную копию. |

### 💡 Типичные сценарии начала работы

- **Первая настройка компьютера**:
  ```bash
  git config --global user.name "Ivan Ivanov"
  git config --global user.email "ivan@example.com"
  git config --global core.editor "code --wait" # Пример для VS Code или vim/nano git config --global core.editor vim/nano

### Настройка удобных сокращений (aliases):
  ```bash
  git config --global alias.co checkout
  git config --global alias.br branch
  git config --global alias.ci commit
  git config --global alias.st status

# Полное руководство по основам Git: Локальная работа и удалённые репозитории

Это краткая, но исчерпывающая шпаргалка по жизненному циклу файлов в Git, фиксации изменений и синхронизации с удалёнными репозиториями.

---

## 📚 Часть 1: Локальная работа и жизненный цикл файлов

### 📝 Краткая сводка
1. **Состояния файлов**: Файлы бывают *отслеживаемыми* (Git знает о них) и *неотслеживаемыми* (новые файлы). Отслеживаемые файлы могут быть неизменёнными, изменёнными или подготовленными к коммиту (проиндексированными).
2. **Индекс (Staging Area)**: Промежуточная область подготовки. Чтобы изменение попало в коммит, его нужно сначала добавить в индекс.
3. **Игнорирование**: Файл `.gitignore` позволяет исключить из отслеживания автоматические или временные файлы (логи, артефакты сборки).
4. **Просмотр изменений**: `git status` показывает, *какие* файлы изменены, а `git diff` показывает, *что именно* изменилось в коде (построчно).
5. **Управление файлами**: Git предоставляет команды для безопасного удаления (`git rm`) и переименования (`git mv`) файлов.

### 🛠️ Шпаргалка по локальным командам

| Команда | Что делает |
| :--- | :--- |
| `git status` | Показывает состояние файлов (изменённые, проиндексированные, неотслеживаемые). |
| `git status -s` | Краткий вывод статуса (`M` — изменён, `A` — добавлен, `??` — неотслеживаемый). |
| `git add <файл>` | Добавляет новый файл под контроль версий или индексирует изменения в существующем. |
| `git diff` | Показывает изменения в файлах, которые **ещё не** добавлены в индекс. |
| `git diff --staged` | Показывает изменения, которые **уже** добавлены в индекс и войдут в следующий коммит. |
| `git commit -m "сообщение"` | Создаёт снимок состояния (коммит) всех проиндексированных файлов. |
| `git commit -a -m "сообщение"` | Автоматически индексирует и коммитит изменения во **всех уже отслеживаемых** файлах (пропускает `git add`). *Новые файлы не добавляет!* |
| `git rm <файл>` | Удаляет файл из индекса Git и из рабочего каталога на диске. |
| `git rm --cached <файл>` | Удаляет файл только из индекса Git, но **оставляет** его на диске (полезно для исправления ошибок в `.gitignore`). |
| `git mv <старое> <новое>` | Переименовывает или перемещает файл и сразу подготавливает это к коммиту. |

### 💡 Типичные локальные сценарии
- **Добавление нового файла**: `git add README.md` → `git commit -m "Добавлен README"`.
- **Исправление бага**: `git diff` (проверка) → `git add app.js` → `git commit -m "Исправлена ошибка"`.
- **Очистка от "мусора"**: Добавить `*.log` в `.gitignore` → `git rm --cached -r logs/` → `git commit -m "Удалены логи из отслеживания"`.

## 🌐 Часть 2: Работа с удалёнными репозиториями

### 📝 Краткая сводка
Удалённые репозитории — это версии проекта, хранящиеся «где-то ещё» (в интернете или локальной сети). 
1. **`origin`** — имя удалённого репозитория по умолчанию при клонировании.
2. **Получение данных**: `git fetch` только скачивает изменения, не трогая ваши файлы. `git pull` скачивает изменения и сразу пытается слить (merge) их с вашей текущей веткой.
3. **Отправка данных**: `git push` загружает ваши локальные коммиты на сервер. Если на сервере есть новые изменения, `push` будет отклонён до синхронизации.
4. **Управление ссылками**: Вы можете добавлять, переименовывать и удалять ссылки на удалённые репозитории.

### 🛠️ Шпаргалка по удалённым командам

| Команда | Что делает |
| :--- | :--- |
| `git remote` | Выводит список имён настроенных удалённых репозиториев. |
| `git remote -v` | Выводит список репозиториев с URL-адресами для чтения (`fetch`) и записи (`push`). |
| `git remote add <имя> <url>` | Добавляет новый удалённый репозиторий и присваивает ему короткое имя. |
| `git fetch <имя>` | Загружает новые данные и ветки из репозитория, **не изменяя** вашу текущую рабочую копию. |
| `git pull` | Загружает изменения из удалённой ветки и **автоматически сливает** их с вашей текущей локальной веткой. |
| `git push <имя> <ветка>` | Отправляет ваши локальные коммиты указанной ветки в удалённый репозиторий. |
| `git remote show <имя>` | Показывает подробную информацию об удалённом репозитории (URL, отслеживаемые ветки, настройки pull/push). |
| `git remote rename <старое> <новое>` | Переименовывает удалённый репозиторий (автоматически обновляет имена веток, например, `pb/master` → `paul/master`). |
| `git remote remove <имя>` | Удаляет ссылку на удалённый репозиторий и все связанные настройки отслеживания. |

### 💡 Типичные сценарии синхронизации
- **Синхронизация перед работой**: `git pull` (быстро) или `git fetch origin` + `git merge origin/main` (безопасно, с предварительным просмотром).
- **Публикация своих изменений**: `git push origin main`. *Если отклонено: сначала сделайте `git pull`, разрешите конфликты, затем повторите `push`.*
- **Добавление репозитория коллеги**: `git remote add colleague https://...` → `git fetch colleague` → работа с веткой `colleague/branch`.

## ⚠️ Важные примечания и лучшие практики

1. **Безопасность `fetch` vs `pull`**: 
   - `git fetch` абсолютно безопасен: он только скачивает данные в фоновый кэш Git.
   - `git pull` сразу меняет ваши файлы. Используйте его, когда уверены, что хотите слить изменения прямо сейчас.
